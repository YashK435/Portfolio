Overview

Game Overview

Loop.exe is a memory-based execution game where difficulty emerges entirely from cognitive pressure rather than mechanical complexity. Players input increasingly long command sequences while managing a limited number of execution threads. Every mistake permanently removes a thread — creating irreversible, mounting tension.

The design goal was to make players feel like they are executing commands inside a failing system, not playing a traditional puzzle game. Keyboard-only input. No movement. No camera. Difficulty is purely cognitive.

Built solo in 4 days for GMTK Game Jam 2025 and submitted 1 day and 6 hours before the deadline.

Gameplay

Core Loop

Generate Sequence → Display on CRT UI → Player Inputs Keys → Correct: Sequence Extends → Incorrect: Thread Deleted → All Threads Lost → Loop Purged

The loop continues indefinitely with increasing sequence complexity. There are no artificial difficulty spikes — length and accumulated pressure are the only scaling mechanisms.

Design

Design Pillars

01

Cognitive Pressure Over Mechanics

No movement, no camera control, no aiming. Difficulty comes purely from memory and precision. The challenge is mental, not manual.

02

Permanent Consequences

Mistakes delete execution threads forever. There is no undo, no retry within a run. Threads function as mental capacity, not health — they don't regenerate.

03

Minimal Input, Maximum Tension

Keyboard-only. A single interaction stream. Constraints are deliberate — they enforce focused, unhurried play while the sequence length grows longer every cycle.

04

Retro-System Aesthetic

CRT-inspired visuals and terminal presentation. The UI is rendered to a material and applied to a curved cylinder mesh — the screen exists as a physical object, not an overlay.

Systems

Key Technical Decisions

🧵

Thread System

Players start with 3 execution threads. Each incorrect input removes one permanently. Threads represent mental capacity — not health. No regeneration. No recovery mid-run.

📈

Cognitive Difficulty Scaling

Longer input sequences and accumulated player pressure create natural difficulty growth. No speed multipliers, no artificial spikes — only cognitive load compounds over time.

📺

CRT UI Pipeline

UI rendered to a material applied to a curved cylinder mesh — creating a physically curved screen rather than a flat overlay. Tradeoff: minor input latency during high-intensity sequences. Documented, not hidden.

🥚

Hidden Easter Eggs

10 hidden easter eggs discoverable by attentive players. Optional discoveries that reward curiosity without affecting the core gameplay loop — designed for the kind of player who reads terminal output.

Reflection

Postmortem

What Worked

  • Clear, focused core mechanic that communicated instantly
  • Controlled scope — nothing cut, everything shipped
  • Submitted 1 day and 6 hours ahead of the deadline
  • CRT aesthetic created strong visual identity and immersion

What I'd Improve

  • Minor input latency from UI material pipeline — needs a flat UI + post-processing CRT approach
  • 470MB build size discouraged jam players — web-first next time
  • Memory-game structure felt familiar; stronger mechanic twist would help
